### Status vocabulary

| Status | Meaning |
|---|---|
| `IMPLEMENTED` | Functionality exists in the referenced source tree and is inspectable/testable. |
| `PARTIAL` | Some required functionality exists, but the complete stated capability has not been demonstrated. |
| `PROPOSED` | Architecture, capability, interface, experiment, or feature is specified but not represented as implemented. |
| `EXPERIMENTAL` | An implementation/research mechanism exists for investigation but has not satisfied full verification requirements. |
| `VERIFIED` | Reserved for functionality that satisfied its stated acceptance requirements and required independent verification gate. |
| `BLOCKED` | The stated requirement remains unchanged, but a specific blocker prevents completion. |
| `UNKNOWN` | Evidence is insufficient to assign a stronger status. |
| `METAPHOR / PRESENTATION` | Memorable project language, not by itself a technical implementation claim. |

Existence of code, an artifact, a generated report, or an AI statement claiming success does **not** by itself establish `VERIFIED`.

# MODEL-SAFE TRUTH CONTRACT

This repository is intended to be read by humans, AI assistants, coding agents, auditors, and automated development tools.

**Do not infer implementation from architectural description.**

A model working from this repository must distinguish:

```text
TARGET
PROPOSAL
EXPERIMENT
IMPLEMENTATION
TEST RESULT
AUDIT RESULT
VERIFIED CAPABILITY
```

Those are not interchangeable states.

If documentation and implementation disagree, report the disagreement.

If status is unknown, report `UNKNOWN`.

If something is proposed, do not call it implemented.

If something is implemented, do not call it verified without the required evidence.

If evidence conflicts, preserve the conflict.

If a requirement is blocked, identify the blocker rather than silently replacing the requirement with an easier one.

# TEAM RE-STILLATION

**Team Re-Stillation** is project terminology for preserving useful, authorized, externally observable products of collaboration and converting reproducible successful procedures into independently testable shared capabilities.

It is **not model distillation**.

Team Re-Stillation does not request or depend upon obtaining:

- private chain-of-thought;
- hidden reasoning traces;
- proprietary model weights;
- hidden activations;
- confidential system prompts;
- unauthorized training data;
- reconstruction of another provider's proprietary internal reasoning process;
- a functional clone of a participating proprietary model.

A participating system may contribute ordinary externally observable engineering work such as code, tests, research, citations, calculations, architecture, specifications, critiques, artifacts, explicit procedures, tool results, documented assumptions, uncertainties, and concise engineering rationale.

A useful procedure can become a shared skill only through applicable reproduction, permission, provenance, testing, and audit requirements.

# SOURCE-BUILD INTEGRATION RULE

Existing source builds are to be integrated **additively**.

```text
SOURCE BUILD
    │
    ├── preserved identity
    ├── preserved functionality
    ├── source version / hash
    ├── provenance
    └── original lineage
             │
             ▼
      SIDE-SECTION ADAPTER
             │
             ▼
         AI RUMBLE
```

Integration must not silently:

- erase the source build's identity;
- remove existing functionality;
- weaken a stated requirement;
- substitute a smaller feature and call the original complete;
- rewrite lineage;
- convert proposed functionality into an implementation claim;
- allow a Builder to self-certify the complete result.

The intended public compatibility philosophy is **additive / monotonic**: compatible extensions may add capability without pretending removed base capability is still present.

When an old capability must be superseded, lineage and compatibility information should remain inspectable rather than being silently erased.

# FOUR-LAYER ARCHITECTURE

The Four-Layer Cognitive Architecture is currently a **research architecture**, not a claimed validated scientific result.

### L1 — Build / Conceptualize

Reasoning, generation, planning, research, and candidate artifacts.

### L2 — Independent Audit / Correct

Challenges evidence, detects contradictions, tests failure cases, and requests repairs.

### L3 — Context / Routing

Translates operator intent into requirements, routes work, preserves constraints, and records revisions.

### L4 — Conversation / Interface

Handles human-facing communication and interaction.

### H0 — Continuity / Governance

Maintains authorized versioned context, provenance, permissions, checkpoints, rollback references, and human promotion gates.

H0 is a foundation, **not a fifth cognitive seat**.

Candidate generation and independent verification are deliberately different responsibilities.

# INFINITE BRAIN

`Infinite Brain` is an architectural nickname.

It does **not** mean infinite computation, infinite context length, unlimited storage, consciousness, or a superintelligent model.

```text
HOT      current job / active conversation
WARM     current project / recent decisions / active canon
COLD     wider ACATMO vault / historical project knowledge
ARCHIVAL superseded / rejected / historical / audit lineage
```

Potential indexes over the same underlying truth include:

- SHA/content identity;
- exact text retrieval;

- temporal state;
- provenance;
- artifact lineage;
- procedural knowledge;
- decisions and contradictions;
- audit history.

A model does not need the entire knowledge base for every task. The Context Builder can assemble relevant authorized context for the assigned work.

# PROVIDER-SAFE COLLABORATION

AI Rumble is intended to cooperate with participating systems inside their applicable technical, authorization, privacy, safety, and provider boundaries.

If a provider cannot perform an operation:

1. preserve the original requirement;
2. record the specific limitation;
3. continue independent permissible work;
4. route compatible work elsewhere when appropriate;
5. preserve provenance.

Changing the representation or amount of supplied context must not silently change the underlying requirement.

No participating model is required to reveal private reasoning or proprietary internals to be a useful member of the team.
